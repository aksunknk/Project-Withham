# クラウド同期 設計メモ（F14）

**状態:** 設計のみ完了。実装は見送り（個人利用・低コスト優先）。

## 結論

現状の **JSON バックアップ（データタブ）** で機種変更・再インストールは足りる。  
有料クラウドや自前サーバーを前提にした同期は、運用コストと複雑性が価値を上回るため **未実装のまま凍結** する。

## 要件（将来実装する場合）

| 項目 | 方針 |
|------|------|
| 目的 | 多端末・自動バックアップ |
| データ主権 | 端末 SQLite が正。クラウドは複製 |
| 衝突解決 | last-write-wins（行単位: `pet_id` + `date`）または手動マージ UI |
| 認証 | 個人利用なら端末ローカル鍵 + 任意アカウント。SNS 認証は再利用しない |
| コスト上限 | 無料枠内（例: 個人用オブジェクトストレージ + 手動トリガ） |

## 候補アーキテクチャ（実装時の単一路線）

1. 既存 `buildBackupObject` / `importBackupObject`（format v2）を同期ペイロードとして再利用する。
2. アップロード先は「ユーザーが選んだクラウドストレージ」（Drive / WebDAV 等）とし、自前 API は作らない。
3. 自動同期はオプトイン。デフォルトオフ。競合時はインポートと同様のマージ/置換ダイアログ。

## 非目標

- リアルタイム共同編集
- SNS / フォロー / 公開プロフィールとの連携
- 有料 BaaS（Firebase 有料プラン等）への依存

## 再開条件

次のいずれかが顕在化したときだけ設計を実装フェーズに上げる。

- 複数 Android 端末での日常運用が必要になった
- JSON 手動バックアップの摩擦が実害になった
- 無料かつメンテ負荷の低いストレージ経路が確定した
